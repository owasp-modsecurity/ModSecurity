# Finding, understanding, and changing features

## Sources and scope

This feature map applies to the official ModSecurity commit `effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729` on `v3/master`. All product descriptions cite implementations at that commit. The suggested reading order and investigation workflows are recommendations for this working repository.

The map connects specific features to their source locations and existing tests. A named test file is a starting point for investigating a topic; it does not establish complete test coverage or a successful test run. Record commands and actual verification results in the current work status. Build and test instructions are in [build-and-test.md](build-and-test.md).

## 2. From rule text to an executable ruleset

`RulesSet::loadFromUri` creates a parser `Driver`, calls `parseFile`, and incorporates the result on success. The `load` overload processes rule text; `getParserError` returns stored parser errors. The `modsec-rules-check` utility uses these loading functions and reports errors, but does not itself execute an HTTP transaction. Sources: [RulesSet loaders](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/rules_set.cc#L50-L110), [rule checker](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/tools/rules-check/rules-check.cc#L38-L92).

Then determine whether the error occurs while recognizing a token, constructing an object, running its `init` method, or loading an included file. ## 3. How rules are actually evaluated

`RulesSet::evaluate` selects the rules for a phase. Among other things, it accounts for `allow`, markers, `skip`, and configured exclusions. After evaluating a rule, it clears the match variables; if the transaction contains a disruptive intervention, it stops further rule evaluation for that phase. Source: [RulesSet::evaluate](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/rules_set.cc#L121-L234).

`RuleWithOperator::evaluate` is the central entry point for a rule with an operator. The following steps can be traced directly there:

1. Check for rules removed by transaction-specific exclusions.
2. Determine the final variable selection, including exclusions.
3. Resolve the `VariableValue` results for each variable.
4. Apply transformations to the value being inspected.
5. Apply the operator to the resulting values.
6. On a match, update match data and provenance references, and execute the corresponding actions.
7. For a rule chain, evaluate the child rule and follow the path for a complete match.

Source for this sequence: [RuleWithOperator::evaluate](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/rule_with_operator.cc#L199-L360). Action effects are also separated between [executeActionsIndependentOfChainedRuleResult](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/rule_with_actions.cc#L202-L243) and [executeActionsAfterFullMatch](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/rule_with_actions.cc#L246-L296). The simplified statement that all actions run only after the entire chain has matched would therefore be incorrect.

Existing test entry points include [`actions.json`](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/test/test-cases/regression/actions.json), [`action-block.json`](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/test/test-cases/regression/action-block.json), [`action-allow.json`](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/test/test-cases/regression/action-allow.json), [`config-secdefaultaction.json`](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/test/test-cases/regression/config-secdefaultaction.json), and [`issue-2423-msg-in-chain.json`](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/test/test-cases/regression/issue-2423-msg-in-chain.json).

## 4. Operators: the specific condition of a rule

The `Operator` base provides interfaces for initialization and evaluation. `evaluateInternal` handles operator negation. `Operator::instantiate` is a factory used by the unit test runner. The SecLang grammar also constructs concrete operators directly. Changing a factory must therefore not be equated with a complete language extension. Sources: [Operator base](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/operators/operator.h), [negation/factory](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/operators/operator.cc#L73-L180), [unit test runner](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/test/unit/unit.cc#L78-L115), [grammar](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/parser/seclang-parser.yy#L934-L1103).

### Special behavior of `@rx`

At the inspected commit, `MODSEC_REGEX_DOLLAR_ENDONLY` helps determine the multiline mode passed to `Regex`. Expressions without macros are prepared in `Rx::init`; when the parameter contains a macro, `evaluate` constructs the expression from the current macro value. Regex errors and match-limit errors are handled separately. A reproduction should therefore record the build option, exact pattern, macro value, and input bytes. Sources: [Rx implementation](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/operators/rx.cc#L29-L101), [Regex utility](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/utils/regex.cc), [associated regression case](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/test/test-cases/regression/operator-rx-dollar-endonly.json).

### Special behavior of libinjection

`DetectSQLi::evaluate` distinguishes `LIBINJECTION_RESULT_TRUE`, `FALSE`, and `ERROR`. It uses `isMaliciousLibinjectionResult`; the code explicitly handles the error path separately and can store the input value in `TX.0` when `capture` is used. Changes in this area should therefore consider more than ordinary matches. Sources: [DetectSQLi](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/operators/detect_sqli.cc), [result helper](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/operators/libinjection_utils.h), [error tests](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/test/test-cases/unit/operator-libinjection-error.json).

## 8. Actions, intervention, and logging

### Actions and engine state

An action can set values, add to a message, activate exclusions, or request a disruptive effect. In `executeAction`, disruptive actions are executed only with `EnabledRuleEngine`. Among other changes, `Deny::evaluate` sets the intervention state; `Transaction::intervention` exposes it to the caller. Sources: [action control](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/rule_with_actions.cc#L299-L325), [deny](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/actions/disruptive/deny.cc), [intervention](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/src/transaction.cc#L1366-L1390).

**Suggested investigation when blocking is missing:** Check the rule match, engine state, executed disruptive action, and API caller behavior separately. A logged match alone does not establish that a web server actually blocked the connection or response. The [C example](https://github.com/owasp-modsecurity/ModSecurity/blob/effb6c0fa031a7bddb3253e0b7ab9ca9a18b5729/examples/simple_example_using_c/test.c) provides an API entry point to inspect.

## 11. Diagnostic record for a subsequent chat

For an investigated defect or open question, record the following as a verifiable handover:

1. **Source revision:** Commit, branch, and local changes.
2. **Observation:** The specific error and expected behavior; label hypotheses separately.
3. **Input:** The smallest relevant rule configuration, request data, and necessary response/API steps.
4. **Environment:** Build options and enabled dependencies relevant to the problem.
5. **Path through the code:** Files and symbols actually read or reached in the debugger.
6. **Verification:** Exact command, exit code, and relevant output; explicitly identify missing or skipped checks.
7. **Next step:** The remaining unproven hypothesis and the next concrete check.

This handover is a working convention for this repository. It does not claim that chat histories are automatically saved or reloaded. [architecture.md](architecture.md), [repository-map.md](repository-map.md), and the sources linked here provide the related technical orientation.
